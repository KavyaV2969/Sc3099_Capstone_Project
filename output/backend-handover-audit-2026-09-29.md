### H01 — Incorrect explicit session export across the Singapore date boundary

Requirement: statistics and exports must agree on retained attendance, use Singapore dates, and exclude sessions whose window has not opened. The current contract is in [Attendance and collection bounds](C:/Users/Lenovo/Desktop/Study/SC3099/student-starter/docs/BACKEND-COMPLETION.md:182).

Reproduction through supported APIs: create/enroll/activate; set scheduled start to tomorrow at 00:00 Singapore with a custom check-in window already open; submit a valid check-in. Session updates accept this timing, and the submission is approved. Session statistics report one check-in. Explicit JSON export returns:

```json
{"summary":{"total":0,"approved_attendance":1},"records":[],"coverage":{"denominator_available":true}}
```

Cause: `_row_query()` applies `session_filters()` with end defaulting to today even for an explicit session, while `export_session()` computes attendance from a separate, unfiltered retained-record query. This produces a contradictory response and omits the same record from CSV.

Required correction: use one consistent retained selection for explicit session rows and summary; preserve course-report defaults, cancellation and retention rules. Test JSON and CSV at the next Singapore date with an open custom window. No schema or new interface is necessary.

### H02 — Incorrect approved attendance after administrative account reactivation

Requirement: append newly eligible students while a session is active; approved eligible students count as attendance; later changes must not remove historical roster evidence. See the same [roster contract](C:/Users/Lenovo/Desktop/Study/SC3099/student-starter/docs/BACKEND-COMPLETION.md:184).

Reproduction, entirely through supported APIs: enroll two active students; deactivate one; activate the session; reactivate the student via `/admin/users/{id}/activate`; submit that student's attendance. The check-in is `approved`, and `by_status.approved=1`, but `approved_attendance=0` and attendance rate is zero. The roster captured only the other student.

Cause: `capture_roster()` correctly excludes inactive accounts. `_set_account_status()` reactivates the user without appending newly eligible active-session rosters. The generic administrative [update_user](C:/Users/Lenovo/Desktop/Study/SC3099/student-starter/module2-backend/app/routers/users.py:112) has the same omission by inspection. Check-in eligibility checks account/enrollment, while `attendance()` counts only roster members. The token-activation route already handles roster inclusion correctly.

Required correction: keep account eligibility, roster inclusion and approved attendance consistent on both supported administrative reactivation paths. Reuse the existing roster helper with the existing lock order; append only newly eligible students to known active rosters, preserve closed/legacy history, and do not remove prior students. Cover the demonstrated lifecycle and a concurrent activation/check-in case. No new table or policy layer is needed.

### H03 — Incorrect retention coverage for a wholly expired explicit date range

Requirement: supported coverage must be truthful; unavailable history must not be classified as absence. The contract requires unknown denominators/rates to be disclosed rather than invented.

Reproduction: request course statistics with explicit `start_date=now−60 days`, `end_date=now−45 days`. The API returns 200 with start clamped to now−30 days **after the returned end**, `limited_by_retention=true`, `denominator_available=true`, and `overall_attendance_rate=0.0`.

Cause: [reporting.window](C:/Users/Lenovo/Desktop/Study/SC3099/student-starter/module2-backend/app/services/reporting.py:23) validates ordering before clamping, then returns an inverted interval. The query finds no sessions; `all([])` declares the denominator available. This is unavailable history, not evidence of zero attendance. The shared function also affects course export filtering.

Required correction: validate the supported interval after retention clamping. A controlled 422 for no overlap is the smallest consistent choice, matching the already-rejected old end-only request; alternatively return coherent unavailable coverage with null rates. Never return an inverted supported range. Cover fully expired, partially overlapping, empty current-period, and end-only requests; preserve genuine zero attendance for retained known rosters.

## 3. Backend Architecture Audit

**API structure.** Existing routers under `/api/v1` cover auth, users, administration, courses, enrollments, sessions, check-ins, devices, statistics, exports and audit queries. The running OpenAPI has 45 path entries, many with multiple methods; the briefing's “~50 endpoints” is not evidence of a missing endpoint. `/health` and `/metrics` are outside the prefix. Arrays remain arrays where documented; flagged attendance uses the envelope. No additional service/endpoint is needed for the findings.

**Database models/migrations.** Eight application tables with relationships, enrollment/check-in uniqueness, state/range checks and relevant indexes. GPS accuracy is correctly nullable after 0009; supplied negative values remain invalid. Activation digest/expiry, device revocation and retained roster use existing storage. Frozen readiness checks columns/constraints/indexes and intended trigger/functions/enabled state. The append-only audit trigger is enabled ALWAYS in the inspected PostgreSQL deployment. Historical recovery to 0006 and current readiness at 0009 are separate. H02 is a missing lifecycle update, not a schema deficiency.

**Authentication/authorization.** JWT access/refresh lifetimes, token types, active-account checks, validated bcrypt passwords and tenth-failure lockout are implemented. Instructors have approved global student reads, but unrelated write/review permissions remain restricted; session mutation ownership is separate from course review rights. Students retain own-data restrictions; TA permissions use current assignments. Public role-selecting registration is the documented grading setup behavior, not a newly discovered implementation defect; deployment expectations must retain that distinction. Token revocation/rotation/logout are documented optional deferrals.

**Course/session/enrollment workflows.** Course activity, student eligibility, ownership, transition guards, enrollment reactivation, partial bulk savepoints, one-use activation and used-session deletion are covered. Known roster snapshots survive withdrawal/admin resets; legacy unknown denominators are not reconstructed. **H02** exposes a gap between account status changes and newly eligible active-session membership. Administrative status changes must be reconciled without rewriting historical closed-session eligibility.

**Check-in workflow.** Attempt audit and transaction release precede remote calls; database/Redis/IP work is offloaded from async request execution. Finalization refreshes and locks eligibility, compares effective verification policy, checks duplicates and cryptographic evidence, and commits attendance/counters/outcome audit together. The approved liveness exception is implemented without fabricating success or redistributing weight. Required face matching still demands camera consent, enrolled hash and image. A 201 response can contain `rejected`/`flagged`; consumers must inspect `status`.

**Geofencing/fraud.** Singapore polygon and public-IP geography are enforced with the first forwarded address and local/private exception required for grading. Unknown accuracy remains null and adds conservative risk; travel inference needs both known radii. The VPN/proxy user-agent signal is a heuristic, not network reputation or cryptographic attestation.

**Integration interfaces.** Activation, optional signed proof, flagged pagination, nullable accuracy/biometrics/rates and retention coverage are documented in the current completion/API addenda.
